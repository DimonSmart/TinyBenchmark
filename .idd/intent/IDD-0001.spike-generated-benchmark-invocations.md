# IDD-0001.spike-generated-benchmark-invocations

## Question

Can source-generated or otherwise precompiled benchmark invocation bodies reduce the measurement overhead of TinyBenchmark's fastest methods compared with delegates prepared at runtime, without sacrificing correct invocation semantics or portability?

This is a **possible future research direction**, not an implementation decision and not a requirement for the current measurement-engine refactoring.

## Constraints

- Preserve the basic TinyBenchmark goal: a lightweight, easy-to-use library.
- Measure the overhead of the **invocation mechanism**, not only whole-run wall-clock time.
- Keep existing public benchmark methods, including parameterized methods, usable.
- Reflection remains acceptable during discovery and preparation; the current refactoring should use prepared delegates/wrappers in the measured path without waiting for this research.
- Assess compilation/build complexity, NuGet packaging, .NET support, AOT/trimming, debugging, and cross-platform behavior.
- Do not introduce source generation or an extra build-time dependency in the current refactoring merely because this question remains open.

## Method

1. Establish a reproducible microbenchmark baseline for a direct method call, a prepared delegate, and the existing Reflection-based invocation.
2. Prototype source-generated wrappers for no-argument and single-argument benchmark methods, including batched Fast measurement.
3. If worthwhile, evaluate generated wrappers versus alternatives such as expressions or cached dynamic call sites, including AOT limitations.
4. Compare performance under tiny workloads (where call overhead dominates), regular workloads, and parameterized cases. Evaluate the generated code's effect on JIT inlining, allocations, and measurement variance.
5. Record the performance win or loss alongside build overhead, target-framework compatibility, maintainability, and developer experience.

## Result

Open. No experiment has been performed or chosen implementation established.

## Recommendation

Research only after the current explicit Fast/Regular/LongRunning strategy refactoring is stable. If evidence demonstrates a meaningful benefit, make a separate decision/spec and implementation task. If not, keep runtime-prepared delegates and close this spike.

**Current non-goal:** this spike must not block or expand the active TinyBenchmark measurement refactoring.
